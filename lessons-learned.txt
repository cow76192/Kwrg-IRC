§0 读法（任何会话开场）
────────────────────────────────────────────────────────────────────────────────
【节点形状】每个节点都是同一个形状，层层递归：

    Lx.y  WHAT  一句祈使句规则（标题即是 what）
          EV    可复核证据：命令 / 类型签名 / 行号 / 已合并代码形态 / 用户原话
          WHY   机理：为什么这条规则成立（一句话）
          HOW   动作：下次具体怎么做；可再挂子节点 Lx.y.z 并重复同一形状
   子节点默认继承父节点的 EV，只有它自己有独立证据时才另写 EV。

  L0.1 不通读。先读 §1 §2，再按任务域读对应章节；跨域时至少读 §8 §9。
       EV  规则分布在十余个域、近百条；单次任务通常只触发 1–2 个域。
       WHY 规则与域强绑定，通读挤占上下文预算且记不住。

  L0.2 优先级：用户当轮指令 > 本文件 > 模型默认习惯。冲突即停下问，不自行裁量。
       EV  本文件全部条目都是"用户改了我的代码"的产物 → 用户意图天然更高。
       HOW 一句话指出冲突 + 列出两种做法 + 请用户裁定；先不动手。

  L0.3 不可复核的推断必须写成 "结论 (待验：验证方式)"。
       EV  旧条目里"类在 mod init 时加载 → 那时通常没有玩家 → 预览一直 fallback"
           一类结论，全部是静态时序推断，从未在游戏内验证过。
       WHY 读代码能证伪，不能证明运行时时序。

  L0.4 本文件是每个 Kwrg-IRC 会话的固定引用，且由多个代理共同沉淀。
       EV  用户明示：日后每次涉及本 mod 的编写都会先引用本文件。
       HOW  开工第一条动作：读 §0 §1 §2 + 对应任务域章节。报告里不必复述本文件，
            但有意偏离某条时要说明理由。
        L0.4.1 别人的条目可被修正，但必须给出 EV，不许只改措辞（见 A.2.3）。

  L0.5 返工分两类：语义没对齐，与规则/既有实现没检索到；后者加解释无用，要加检索动作。
       EV  本轮两次返工都不是理解偏差：L2.3 已明写"不加注释"，组件已有 activeAnimation；两次都是没查。
       WHY 语义偏差靠复述对齐；检索失败靠"落笔前查一遍"，两者是不同病因。
       HOW 开工查两处（本文件 §2、目标文件已有字段与方法），交卷前再对一遍 §2。

§2 硬约束（用户明示，违反即返工）
────────────────────────────────────────────────────────────────────────────────
  L2.1 不做要求之外的功能。
       EV  无调用方的入口进主干后被整段回退（见 L8.3 L8.4）。
       HOW  想加的写进报告"建议"，不动代码。
        L2.1.1 唯一例外：发现非常严重的 bug。仍须先报告，得到确认后才动手。
               WHY  严重与否由用户判定，不由我判定。

  L2.2 改既有签名 / 参数 / 行为，先报告改了什么再改。
       EV  用户明示的硬约束。
       HOW  先给"改哪、为什么、影响哪些调用点"，等确认；改完再列一次实际改动清单。

  L2.3 不加新注释，不动原有注释。
       EV  用户明示的硬约束。
       HOW  代码自解释；需要解释的写进报告。
        L2.3.1 交卷前过 §2 四项：新注释 / 改签名 / 新入口 / 新文件；命中即撤或先问。
                EV  新加 Javadoc 与行内注释被要求整段移除（L2.3 早已写明）。
                HOW  只问"是否命中"，不问"删起来麻不麻烦"。

  L2.4 缺源码 / 缺 API 就停下问。不猜包名、类名、路径。
       EV  每次猜 API 都错；每次读字节码都对（L3.1 即由此产出方案差异）。
       HOW  javap -c -p 出真实签名；找不到就报告"缺 X，需要你提供"。
        L2.4.1 唯一例外：确信能从外部库或额外目录搜到源码 → 先搜，搜到再继续；
               搜不到立刻回到 L2.4 停下报告。

  L2.5 判据只活一处；不留不可达分支。
       EV  两个相同 function_sync 分支，前一个 return 掉后一个（见 L12.1）。
       HOW  同一判断只写一个 if；出现第二处即抽方法。

  L2.6 分支、计划文档、提交和推送都走用户预先安排的工作流。
       WHY  用户要自己 build + 测试；代理写 master、推送或保留计划文档都会打乱流程。
       HOW  开工前确认当前分支不是 master；是则停并报告。只在用户预建的子分支写代码；计划/方案先给用户审，确认后删除计划文档再写；不 commit、不 push，只交 diff 摘要和建议提交信息。
        L2.6.1 代理只改代码：不 build、不测试、不 commit、不 push、不暂存。
               EV  用户明示：“你只负责在idea里修改，我来提交”“不用build测试，不用commit提交”。
               HOW  改完只报“改了哪几处 + 文件:行 + 建议提交信息”，其余交给用户。
        L2.6.2 出现下列任一信号，立刻停手发问，不自行修补：
               (a) 当前分支语义与任务不匹配；
               (b) 自己上一轮改的代码不在了（被重置/切分支/被覆盖）；
               (c) 用户要求在 master 上改（他忘了先建子分支）。
               EV  用户明示：“发现对应的分支语义不对…/…我让你在master里修改（我忘记创建新子分支了），立刻停下来问我”。
               HOW  停下并报“看到的现象 + 我怀疑的原因 + 请他确认分支/是否重建子分支”，不要用 git 操作去猜。

  L2.7 已推送历史绝不改写；未推送可压成一个提交；force-push 仅在"远端只有
       被取代的那个提交"时配 --force-with-lease。
       EV  用户明示的硬约束。
       HOW  先 git log origin/<branch>..HEAD 确认真实未推送范围。

§3 验证
────────────────────────────────────────────────────────────────────────────────
  L3.1 用字节码/运行时事实替代记忆。
       EV  javap 实测 GuiGraphicsExtractor.text 有 String / FormattedCharSequence /
           Component 三种重载，且各带 shadow 版本 —— 这直接决定了 L8.1 的方案。
       HOW  第三方 jar / class：javap -c -p；MC 类：loom-cache 里的 clientOnly jar。

  L3.2 gradle 在沙箱跑不起来 → 用 javac 全量编译做最低验证。
       EV  依赖 gradle 缓存 + loom-cache 的 clientOnly/common jar 拼 classpath 可全量编译。
       HOW  缓存被清：从 .minecraft/libraries + mods 重建，并解包 Fabric API 嵌套 jar。

  L3.3 逻辑验证走反射 harness。
       EV  测试类放 build/tmp，编进同一 classes，输出写文件再读（否则中文乱码）。
       HOW  跑不了游戏的部分，明确请用户目视确认。

  L3.4 报告固定三栏：已验证 / 未验证 / 待用户确认。
       EV  javac 全量 + 16/16 harness 只证"能对上"，证不了"最短路径、成本可接受"。
       HOW  未验证项必须写清"我需要什么才能验证"。

  L3.5 验证 ≠ 设计验证。
       EV  同 L3.4：16/16 harness 全绿，仍可能是一条更长的路。
       HOW  正确性通过后，仍要在报告里回答"有没有更短的路"（L8.8）。

  L3.6 统计行数/规模不用 PowerShell。
       EV  Measure-Object -Line 在本仓库实测少算 15–20%。
       HOW  Python splitlines 或读工具返回的 totalLines。

  L3.7 长任务不要塞进默认超时的调用。
       EV  渲染/编码类命令超预算被中断，产出半成品文件。
       HOW  显式给大 timeout，或后台运行再轮询产物落地。

  L3.8 沙箱与 PowerShell 具体坑（照抄，别重新踩）
       EV  命名管道被禁；GIT_EDITOR=true 会崩（用 ":"）；多行正则被 CRLF 打穿；
           单引号里的 `r`n 是字面量；git diff -- <path> 偶尔静默无输出。
       HOW  复杂替换用 edit 工具；取 diff 用 git show 或 diff --no-index。

  L3.9 迁移/移植的等价性要两端各一份证据：来源侧行为 + 目标侧分支表。
       EV  1.8.9 Forge patch：cancel 只跳过 onPlayerRightClick、不 return，随后仍 sendUseItem；
            26.1.2 javap：useItemOn 返回 FAIL 直接 return，PASS 才落到 useItem。
       HOW  报告给"来源一行 / 目标一行"对照；给不出就标待验（L0.3）。

§4 Mixin 与第三方互操作
────────────────────────────────────────────────────────────────────────────────
  L4.1 require 按归属分级。
       EV  第三方注入点 require = 0（类缺失由 @Pseudo 跳过，方法改名静默跳过）；
           原版目标 fail-loud（require = 1）。
       HOW  按"目标属于谁"定 require，不统一一个值。

  L4.2 一个 mod 一个 mixin 文件，按归属方分包。
       EV  仓库已有 mixin/cape/ 等按域分包先例。
       HOW  新互操作 → mixin/<owner>/ 新包，不往公共 mixin 文件里塞。

  L4.3 能"取消 + 接管"就别"检测 + 降级"。
       EV  ServerResourceBypass 直接 ci.cancel()，再把 id/url/hash 转交
           ServerPackManager.handlePush。
       WHY 降级路径要写的守卫，接管路径结构上根本不需要。
       HOW  先问"我能不能直接接管这个动作"；能，就不写 if (failed) 分支。

  L4.4 只读对方的状态字段/常量，不读渲染副产物。
       EV  某 API 返回值实为鼠标相对坐标且带 pose 副作用，调一次整块 UI 永久偏移。
       HOW  调可疑方法前先看它有没有副作用；优先 public 字段。

  L4.5 反射只留一处、缓存一次、失败即永久停用。
       EV  单点 + 一次性日志 + 一次性玩家提示。
       HOW  静态 boolean disabled，失败后所有调用点直接返回。

  L4.6 横切/装饰逻辑挂在唯一出口，不挂入口。
       EV  曾挂 ClientPacketListenerMixin.onSendChat，漏掉 /ic、/icall；
           现挂 IrcClient.sendMessage(:278)，全路径覆盖
           （ChatSuffixModule.decorateIrcSafely 在 :290 与 :353 调用）。
       HOW  先找到"所有路径都必经的那一行"，再把装饰接在那里。
        L4.6.1 模块管"怎么装饰"，mixin 管"何时算 IRC 消息"，职责不交叉。

  L4.7 扩展既有签名时保留一个委托旧签名的重载。
       EV  displayFormattedMessage 加参后保留原 6 参重载 → 调用点零改动。
       HOW  新参数给默认值的重载转调新签名。

§5 全局渲染状态
────────────────────────────────────────────────────────────────────────────────
  L5.1 绝不把 pose / scissor 留在栈上。
       EV  只清标志、不真弹栈的"自愈"是 bug：标志清了矩阵还压着 → 整个 UI 永久偏移/被裁剪。
       HOW  push 与 pop 写在同一分支内成对出现；动手前先数配对
            （enableScissor/disableScissor 必须同分支）。

  L5.2 Mixin 没有 try/finally → 兜底只能是"每帧开头检测残留并真释放"。
       EV  Mixin 只能注入 HEAD / RETURN，包不住整个方法体。
       HOW  帧首检测残留 → 真正 pop/disable + 一条 WARN（不静默修复）。

  L5.3 每一层都要查门禁。
       EV  渲染器改完还要查 mixin 层；Tab 功能不应被岛的开关挡住。
       HOW  从最外层入口到 draw 调用，逐层列出"这次该不该画"。

  L5.4 帧作用域状态显式复位，不用时间窗猜。
       EV  帧间隔受 FPS 与卡顿影响不可控 → 时间窗判据必然有误判窗口。
       HOW  每帧开始置位、结束复位；不写 if (now - last > 500)。


────────────────────────────────────────────────────────────────────────────────
§6 配置迁移
────────────────────────────────────────────────────────────────────────────────
  L6.1 判据用 has()，不用取值。
       EV  ConfigMigrator.migrate 全篇 jsonObj.has(...)；false 是有效值，不是"没有"。
       WHY 用 getBoolean() 判 false 会把"用户关掉"读成"未设置"，
           升级后功能自己回来了（真实 bug：关掉阴影的用户阴影复活）。
       HOW  忠于 ConfigMigrator:35-42 的形状：
        L6.1.1 if (obj.has(old)) → if (!obj.has(new)) obj.add(new, obj.get(old))
        L6.1.2 再 obj.remove(old)；只在缺失时写、写完删旧键。

  L6.2 忠实搬运原值，不改写。
       EV  同上：值原样 add，不做类型转换、不取反。
       HOW  迁移只做"搬家 + 删旧键"两件事。

  L6.3 幂等：连跑两次输出逐字节一致。
       EV  迁移每次启动都跑；非幂等则每启动一次改写一次用户文件。
       HOW  测试台跑两遍比对 hash。

  L6.4 永远不要把 true 当"安全默认"。
       EV  同 L6.1 的真实 bug：关掉阴影的用户升级后阴影复活。
       WHY  缺字段补 true = 替用户打开一个他明确关过的功能。
       HOW  新字段初值取"副作用最小"的那个值。

  L6.5 用真实旧版 JSON 做一次性测试台。
       EV  覆盖矩阵：旧全量 / 开关组合 / 已有新格式 / 幂等 / 最老别名。
       HOW  "字段存在"不算验证，要比对最终渲染或行为。

  L6.6 旧键迁移成本极低，别急着删。
       EV  用户开发档里可能有旧键（chatSuffixText 即为线上来的旧名，
           ConfigMigrator:44-46 保留了 chatSuffixText → chatSuffix）。
       HOW  删键前先确认"它从未在发布版存在过"；不确定就保留迁移。

§7 安全
────────────────────────────────────────────────────────────────────────────────
  L7.1 远端字符串永不直接进文件路径。
       EV  远端 hash / fileName 参与缓存命名（PlayerCustomizationManager:734
           以 "cache/" 前缀区分远端来源）。
       WHY  拼路径 = 任意 .png 写入。
       HOW  三重校验，任一不过即拒绝：
        L7.1.1 字符白名单
        L7.1.2 normalize()
        L7.1.3 startsWith(baseDir)

  L7.2 替换或绕过原版机制时，把它的保障一起搬过来。
       EV  ServerResourceBypass 取消了原版资源包处理，而 SHA-1 校验正好在那段里。
       HOW  cancel 之前先列"被取消的这段做了哪些安全检查"，逐项在新路径实现。

  L7.3 审计看整条链，不要只 grep 关键词、不要只读半个文件。
       EV  只 grep "sha1" 会误判"没有校验"——校验可能在调用的下游。
       HOW  从入口跟到落盘/落网，读完整方法体。

  L7.4 复用仓库里已有的正确做法。
       EV  已有：日志脱敏 Base64（IrcCapeManager:81）、
           SHA-256（IrcCapeManager:40 / FontManagerHelper:214）、
           配置名校验器（ConfigMigrator.KNOWN_CONFIG_KEYS:17，反射自 IrcConfig）。
       HOW  写新校验前先搜 util/ 与 manager/ 有没有同类。


────────────────────────────────────────────────────────────────────────────────
§8 设计最小性 ★ 最多返工都出在这里
────────────────────────────────────────────────────────────────────────────────
  L8.1 原生 API 能直接吃你手里的数据结构，就不要自造转换层。
       EV  font.split(Component, w) 直接产出 List<FormattedCharSequence>；
           graphics.text(font, line, 0, 0, color, false) 有 FormattedCharSequence 重载。
           中间"序列 → Component"层是纯开销：每行每帧 new N 个 Component + N 个 String，且比原生多跑一整轮 decompose。
       HOW  写转换层之前，javap 数清目标 API 全部重载，列"我的类型 / 它的参数"对照表；
            能对上就删层。
        L8.1.1 我这层删掉会怎样？答不出"会坏"就删。

  L8.2 让序列化格式表达结构，不要往字符串里塞分隔符。

  L8.8 正确性通过 ≠ 设计通过。
       EV  同 L3.4：验证手段只覆盖正确性一维。

  L8.9 先锁定用户所指的具体控件，再复用已有动画通道，不新建状态。

        HOW  用控件文本/截图锁定目标；优先复用该组件已有的动画进度，不另起一套。
        L8.9.1 新建状态前先 grep 目标组件已有的进度/开关字段与 setter，把候选写进方案。

        WHY  press 就提交编辑会和拖动共用副作用，拖动必然先进入编辑。
        HOW  press 记录拖拽起点/偏移；release 按是否移动决定点击或排序；拖动中只画浮层。
         L8.11.1 排序插入位按固定槽位算，不按动画中的邻居位置。
                 EV  PointListDrag.insertionIndex 用被按住行中心对固定槽位取整
                     （合并版注释 "not the animated neighbours"）。
                 HOW  插入位 = f(被拖行位置, 行高, 滚动)；动画只影响显示。

  L8.12 用户领域词和几何量先复述成可执行定义，再写代码。
        EV  合并版把"坐标冲突"改成"点位冲突"，并让 describe 带上 name+visible——冲突也可能来自名称或显隐，旧名词覆盖不了判据全集。
        WHY  同一词或同一几何量有多种解释，晚改会扩散到命令、配置、目录和 UI。
        HOW  开工前把领域词、坐标公式、边界写成一句话复述；命名一次统一，坐标用明确公式；
           文案名词要覆盖判据全集。

  L8.13 状态同步发整份快照，不发增量分片。
        EV  hideArmor 部位：最终版一条消息带 parts 全集、收端整体替换；我发 5 条（总开关+四格），先全隐再纠正，丢一条就留脏状态。
        WHY  增量收敛依赖"每条都到且有序"，快照只依赖最后一条。
        HOW  报文带完整集合；收端整体覆盖、空集合即删除；不逐格 add/remove。

  L8.14 顺序敏感的输出来自 List，不迭代 Map。
        EV  面板四开关用 PARTS.values()（Map.of），迭代顺序未定义，每次启动可能换序；改 List.of 后固定。
        WHY  Map 的迭代顺序是实现细节，不是契约。
        HOW  UI 顺序、序列化输出用 List/数组；Map 只做查找。

  L8.15 让动作失败的守卫，必须同时给出解除该失败状态的出路。
        EV  冲突检测把 flush() 改成失败即阻断 back()/close()，刷新又跳过"有未保存改动"的集合 → 外部改动后既存不了也退不出。
        WHY 只保证不丢数据会把失败变成死锁；安全性与可终止性要一起满足。
        HOW 每个 return/throw 的拒绝分支都问"用户下一步怎么摆脱它"，答不出就补一条放弃并重载。

  L8.16 读-改-写带磁盘基线比较，写失败回滚内存态并返回 false。
        EV  合并版用 loadedContent / diskContent+savedState 作基线，write 前 requireUnchanged，add/delete/rename/setEnabled 失败即回滚。
        WHY 无基线则外部改动被静默覆盖；无回滚则失败后内存与磁盘分叉。
        HOW 每个可变持久对象记住"上次读到的字节"，写前比对，失败恢复旧值并把结果交给 UI。

  L8.17 可恢复失败的 catch 只捕它那一类异常。
        EV  importRoute 用 catch (IllegalArgumentException) 把"名称非法"当"重名"反复重试 → 死循环；改用专用 DuplicateNameException 后非法名直接上报。
        WHY 宽 catch 会把 A 的恢复动作施加到 B 上：循环里是死循环，循环外是静默错误。
        HOW  给可恢复失败定义专用异常；其余异常冒泡到 UI。

  L8.18 移植外部功能按目标仓库既有架构落地，不搬来源仓库的框架。
        EV  IQ 方案带 EventBus/Feature/Action 枚举的多文件改动；合并版 1 mixin + 1 模块，
            方案文档整份删除（用户原话"为什么搞得这么复杂"）。
        WHY  目标仓库没有订阅者时，框架只是多一层跳过。
        HOW  方案第一段先列目标仓库的等价物（模块开关/配置字段/命令入口）。
  L8.19 取消类注入落在能单独取消的那一层，用 PASS 让原版继续。
        EV  方块右键 useItemOn：HEAD 返回 PASS → startUseItem 落到 useItem 扔珍珠、不发交互包；
            返回 FAIL → startUseItem 直接 return，投掷被吞（用户实测"Kuudra 定身做不到"）。
        WHY  1.21.2 起该方法包在客户端预测里，尾部改返回值时包已发出（客户端与服务端分叉）。
        HOW  先 javap 读调用方分支表（Success/Fail/其他），再选返回枚举。
  L8.20 可取消手势要记住起始快照，取消路径按快照还原。
        EV  PointListDrag 取消时 add(min(originalIndex, size-1), remove(index))；
            拖拽期间任何面板打开或列表/文件变化即 cancel（dragEntriesUnchanged）。
        HOW  每个手势都存 originalIndex / 原值，取消分支只做还原。

§9 流程与协作
────────────────────────────────────────────────────────────────────────────────
  L9.1 不为"清理"新增文件。
       EV  抽桥方案 +1 文件 / +31 行；折回既有归属方后净 -33 行 / -1 文件。
       WHY  抽象另起一个类，是把耦合换成了分散。
       HOW  重构 KPI 是"文件数 + 净行数"，两者都要降；新增文件必须在报告里说明结构理由。
             功能改动同理：先定"最少动哪几处"，多改一个文件要能说出不改会坏在哪。

  L9.2 Review 逐条回执：采纳 / 不采纳 + 原因 / 需用户裁定。
       EV  来源通常是 GitHub Copilot、Qwen3.8max 等强模型；强 ≠ 正确；做不到的（Mixin 无 try/finally）要说清物理限制，两份矛盾时明确指出、不折中。
       HOW  每条给「采纳：<理由>」或「拒绝：<物理限制 / 反证>」。
            禁止沉默略过，也禁止照单全收与全盘否定这两种偷懒。

  L9.3 每轮清干净临时产物，并列出"删了什么、还剩什么"。
       EV  用户明示；且证据中间产物（帧 / PDF / pycache）体积远大于成品。
       HOW  交付时附两份清单：已删除 / 仍保留，各带体积。

  L9.4 提交信息必须与 diff 一致。
       EV  97e0db3 的 message 写的是 cape 重构，实际只改了 TextInputPaneComponent
           （+53/-11）。
       HOW  写完 message 用 git show --stat 复核一遍。

  L9.5 追历史不信 commit message。
       EV  同 L9.4：97e0db3 的 message 与 diff 不符。
       HOW  定位"谁引入某段代码"用 git log -S <标识符> -- <路径>。


  L9.6 审 PR 必须结合整个仓库目录，不能只看 diff。
       EV  只看 diff 看不到"这个类已有等价实现"与"这个静态 Map 只进不出"；
           用户原话即"结合整个仓库目录寻找"。
       HOW  读 diff → 找同职责的既有实现 → 再按 L9.6.1–L9.6.3 逐一过。
        L9.6.1 冗余：可安全删除的死代码、可简化的代码、该合并的类。
               HOW  可达性（L12.1）+ 文件数与净行数（L9.1）。
        L9.6.2 可改进：更高效的实现、该释放的缓存与内存、重复模式未抽取。
               HOW  每帧 / 每次调用路径上有没有重复分配；静态 Map 有没有出口。
        L9.6.2.1 冲突检测的基线不要放在刷新路径上做全量读盘与序列化。
               EV  WaypointFiles.refresh() 每秒对每个文件 readText + serialize 全量点位来算 hasUnsavedChanges。
               HOW  基线用 mtime+size 与脏标记；只有候选变化才读文件、才序列化。
        L9.6.3 安全：超大文件或超大包炸服、null 未判、远端字符串进路径（L7.1）。
               HOW  每个外部输入都要有尺寸上界与判空。

  L9.7 用户要求精简时，同时压缩验证轮次和交付篇幅。
        WHY  反复自证和长版材料消耗时间，却不提高正确性。
        HOW  每轮最多一次全量编译 + 一次 diff 检查；对外材料默认一句话，长版先问。

  L9.8 编辑后立刻复读目标文件，确认结果与意图一致。
       EV  一次 edit 的 old/new 写反，onUseItem 变成两份重复方法，直到 read 才发现。
       HOW  编辑后 read 关键区间或 grep 方法名计数；提交前编译一次。
  L9.9 用户写作习惯：结论先行、动词开头、用产物代替描述、用反例下需求。
       L9.9.1 短指令按字面执行，不扩写。
              EV  "该删的删"、"直接在 idea 里改"、"解决第一个副作用"即是完整需求。
              HOW  缺判据才问（L2.4）。
       L9.9.2 用具体产物定位问题，先打开再动手。
              EV  IQ.zip、ctjs jar、B 站 31–34s、23% 进度条截图。
              HOW  路径/链接/截图/时间点先读，不拿描述猜。
       L9.9.3 反例与追问即验收标准，不接受"应该没问题"。
              EV  "现在做不到 X"、"完全一样吗"、"有可能被 ban 吗"。

────────────────────────────────────────────────────────────────────────────────
  L11.1 布局协议相同就用原图，不重绘。
       EV  isStandardCape(w, h) 判 w == h*2（:100 / :170）；标准布局整图缩放，

       WHY  重绘 = 二次重采样：慢 + 糊 + 限死素材。
       HOW  先判协议，再决定走哪条路径。

       EV  拉长间隔会连总时长一起改；跳帧 + 累加能把总时长还原成原始值。
       WHY  拉长间隔改变动画观感；跳帧保持原始时序。

  L11.4 同一判定收口到单一决策点，标准路径要有 fast path。
       EV  processCapeFrame 三个调用点（:758 / :763 / :868）都进同一函数；
            标准尺寸固定 block × block/2。
       HOW  新出图路径一律转调该函数；标准尺寸在入口提前返回，不进重采样。

§14 总纲（提交前逐条对一遍）
────────────────────────────────────────────────────────────────────────────────
  宁可删掉一套需要精确对齐的东西，也不要写守卫兜它；
  宁可每帧显式复位状态，也不要靠标志位"看起来配平"；
  宁可让迁移忠实搬运 false，也不要写成 true；
  宁可删掉不可达分支，也不要留两个同名分支；
  宁可让格式表达结构（字段），也不要往字符串里塞分隔符；
  宁可一次发完整快照，也不要拆成多条增量；宁可给旧消息加字段，也不要新造消息名；
  宁可把功能挂在唯一出口，也不要挂在一个入口；
  宁可让原生重载直接吃你手里的数据结构，也不要自造一层转换；
  宁可把两条路都读完再选，也不要凭"看起来要自己管状态"排除原生路径；
  宁可加守卫统一两个不一致的分支，也不要拿"不是我要求的变更"当借口；
  宁可不加"以后可能用"的入口，也不要让没有调用方的 API 进主干；
  宁可报"我为什么没用更短的路"，也不要让正确性验证冒充设计验证；
  宁可什么都不加，也不要加一个用户没要的功能。

  L15.1 会改像素的决定先出表，再动手；结构可以自己定。
       EV  三次返工：作用域 A→B（只淡底板 vs 整层）、颜色全量还原（先给新旧对照表后才对）、
            rowText 撞色（浅色档 0x5C6875 与被透明度压暗后的面板底几乎同值）。
       WHY 用户对“看不见的结构”容忍度高，对“看得见的一个像素”零容忍。
       HOW  任何改可见结果的决定，先给“旧值→新值→影响面（哪几屏）”三列表。

  L15.2 批量替换必须带断言并在脚本内反查，静默成功最贵。
       EV  五连：`join()` 早于 `ensure(import)` → 4 文件缺 import；`String.replace` 未断言 →
            `withAlpha/opaque` 没删却打印成功；CRLF 与 pattern 不匹配 → 多行替换静默失败；
            同一 helper 被插入两次（靠 index 扫描删除）；抽离服务时 `slice(len-1)` 少切一行 →
            新类多带一个结束括号（43/44）。
       WHY  事后 grep 只能发现错误，脚本内 assert 能阻止错误落盘。
       HOW  每次替换记录命中数，0 命中即报 MISS；改完 `grep -c` 反查并 `git diff --shortstat` 对账。

  L15.3 换行符是仓库事实：读文件先测 \r\n，pattern 按实际换行符展开。
       EV  一次 `join("\n")` 把 41 个文件由 CRLF 改成 LF，靠 `git checkout --` 还原 27 个；
            改写脚本再次 `split(/\r?\n/).join("\n")` 规范化 17 个文件（autocrlf 掩盖了 diff）。
       WHY  Windows + autocrlf 下 diff 看不出，sed/perl 静默不匹配。
       HOW  `grep -c $'\r'` 先判；改写后看 `git status` 是否冒出整目录改动。

  L15.4 继承/接口类方案，第一段先写“谁不能继承、为什么”，再给选项。
       EV  GuiTheme 与 GuiSurface 两次被推翻，根因是先建类型、后解释 FlowLayout 的单继承约束。
       HOW  方案首段固定写“继承链 + 阻塞点（哪个类必须 extends 别的）”。

  L15.5 性能取舍要给出“每帧 N 次 × 单次成本”，答不出数字就标 (待验)。
       EV  review 两次点名：描边派生每帧 2 次 HSB、色调访问器每帧约 20 次 now()。
       HOW  结论行带数字；无实测时写“未实测”，不写“可忽略”。

  L15.6 结构改动与可见改动分两次提交；一次 17 文件 +250/−96 的 diff 只能整体评审。
       HOW  先落结构（像素不变）→ 再落取值（附对照表）→ 再落健壮性修复。

  L15.7 “随口一说的数”只表示语义，落地必须自己给可解释的公式。
       EV  用户原话：“例如直接 hsl 中的某一项 -10 之类的 —— 绝对不要用这个数这么写”。
       HOW  例子里的数字不进代码；改成“亮度 ±0.055、饱和 ×1.1”这类可读档位并说明方向随明暗自适应。

  L15.8 可见改动交付前跑三档自查：默认色 / 纯白 / 中间灰，各配 100% 与 30% 透明度。
       WHY  本次会话 6 次返工全部落在“某一档下文字或卡片失去对比”。

  L15.9 用户用“截图 + 一句现象”评审，不给修法；期望的回复是“根因 + 选项 + 推荐”。

       HOW  回复先一句根因（带文件:行），再给 2–3 个互斥选项，最后标推荐并说明代价；收紧“识别范围”前先拿 3–5 条用户真实样本做验收表。

§A 更新协议（本文件如何迭代）
────────────────────────────────────────────────────────────────────────────────
  A.1 每轮结束做六步：
        A.1.1 取差集：git diff <我的提交> <合并后代码>
        A.1.2 归类：每条差异落到 §2–§8 某一节；归不进的说明出现了新域
        A.1.3 抽象：只留"能迁移到别的文件/别的功能"的规则，
              丢掉具体文件名、函数名、行号（行号只在 EV 里作锚点）
              再问"读者下一步要做什么动作"；答不出说明它是事实记录，删或降级为 EV。
        A.1.4 落条目：一条 EV + 一句 WHY + 一句 HOW；EV 必须可复核
        A.1.5 去重：已有条目只补 EV，不并列新条目
        A.1.6 被回退的改动直接进 §8 或 §14——"我做过但被删掉"是最强证据

  A.2 准入规则
        A.2.1 有可复核 EV → 收
        A.2.2 只有"感觉" → 标 (待验)，不当作规则
        A.2.3 与现有条目冲突 → 改写现有条目并在 A.4 记变更，不两条并列

  A.3 长度上限
        A.3.1 单条（含挂在其下的子节点）≤ 8 行；EV 为列表时每项一行、≤ 5 项。
        A.3.2 上限看"规则行"＝所有 L 节点 span 之和（不含目录、章节标题、分隔线），
              ≤ 360 行；全文 ≤ 800 行。
              超了先合并相邻条目，再删最久未触发的。
